**Goal:** Visitors can play Chkoun?, a daily guess-the-footballer game in three locales, share a spoiler-free grid, keep a streak, and read where the data and photos come from and what Kora stores about them.

**Architecture:**
- Pure engines with no I/O: `src/engine/chkoun/` (the Tunis day, tiles, calendar draw, share text, streak) and `src/engine/names/` (search keys). Property-tested.
- The day's answer lives only in Postgres (`puzzles`). A generator writes 30 days ahead from a secret seed (`CHKOUN_SEED`, Vercel only), at deploy and every night; Jalel swaps and pins in `/admin/chkoun`; a database trigger refuses to change a day less than 48 hours before it starts.
- The game page is a static shell per locale. Guesses go to `POST /api/chkoun/guess` with a signed game-state token (HMAC). The server keeps no per-game state; it reads today's answer once per instance (and once a day through Redis when Redis is on) and the footballers' tile values from `data/pool.json` on the server.
- Finished games are recorded in Upstash Redis under an anonymous visitor id (a first-party cookie), and copied to the `results` table once a night by a Vercel Cron route. With Redis off, the game is fully playable and everything is "saved on this device".
- Photos are copied from Commons into `public/photos/` by the nightly job; they appear only on the result screen, with their credit, and on the Sources page.

**Tech:** Next.js 16.3.8 (App Router, Proxy, route handlers, server actions, metadata), next-intl 4.14.9, Prisma 7.10 + `pg`, `@upstash/redis` 1.39.0, Vitest 5 (+ `fast-check`, new dev dependency), Playwright 1.63 + `@axe-core/playwright`, Lighthouse CI 0.15.1. Pipeline scripts run with `node file.ts` (P24).

**Done for the sprint means:** the hub's Chkoun? card links to `/ar/chkoun`, `/tn/chkoun` and `/fr/chkoun`; a visitor can win or lose today's puzzle on a 320 px phone in each locale, share the grid, and see the card with photo or silhouette and credit; `/sources` and `/privacy` exist in three locales; `/admin/chkoun` shows the next 30 days and Jalel can swap or pin an unfrozen day; the nightly copy has run once in production (or Redis is knowingly off); `bash check.sh` passes, including the answer-leak tests and Lighthouse on `/ar/chkoun`; Jalel has seen the screenshots and approved or replaced the drafts that block the merge.

### New choices for Jalel (answer before Task 7; silence takes the recommendation)

**N1. The visitor id.** The server needs an anonymous id to know that two finished games belong to the same visitor.
- (a) A cookie set by the server when a visitor finishes his first game, only while Redis is on: a random number (UUID v4), name `kora_v`, readable by the server only (HttpOnly, Secure, SameSite=Lax), sent only to `/api/chkoun/*`, kept 13 months. Pages stay static. Scripts on the page (including anything Facebook injects) cannot read it.
- (b) A random id in the browser's local storage, sent by the game's script in a header. Same privacy weight under ePrivacy (both are storage on the device), but readable by any script, and Instagram is reported to wipe local storage.
- Either way it holds no personal data, is never sent to PostHog or Sentry, and is created only when a result is kept on the server. The privacy page then says "one strictly necessary cookie". Hub-polish removed the only other cookie (H4).
- **Rec: (a).**

**N2. How results reach Postgres every night.** The GitHub nightly job has no database access (P17).
- (a) A Vercel Cron job at 02:40 UTC calls `/api/cron/nightly`, protected by `CRON_SECRET`. It copies the last 7 days from Redis and tops up the calendar. Hobby allows daily crons; it runs on production only.
- (b) Copy at each deploy only. Deploys happen when Jalel merges a nightly pull request, so a week without merging loses results.
- (c) Give the GitHub job a database secret. Reverses P17.
- **Rec: (a).** Cost: one Neon wake a night (about 5 minutes at 0.25 CU, about 0.6 CU-hours a month of 100) and about 10 Redis commands a night.

**N3. How long Redis keeps things, and what Postgres keeps.**
- (a) A day's finished games stay 8 days in Redis (7 nights of retries if a copy fails), then expire. A visitor's streak numbers stay 13 months after his last game. Postgres keeps, per game: day, visitor id, solved, number of guesses, and the colour grid (no guessed names). Postgres keeps results until Jalel decides otherwise.
- (b) Same, but Postgres keeps only solved and the number of guesses.
- **Rec: (a).** The grid lets later sprints measure tile fairness without names.

**N4. Rate limit.**
- (a) With Redis on: at most 80 guesses per 10 minutes per network address, counted under a salted hash of the address (the address itself is never stored); over the limit, "try again in a few minutes". With Redis off: no limit beyond Vercel's own.
- (b) No rate limit in Sprint 2.
- **Rec: (a).** It stops a script from walking the whole list to find the answer, at about 1.2 Redis commands per guess.

**N5. Which tiers on which day.** Owner rule: D never, C only at weekends. Weights are a proposal.
- (a) Monday to Thursday: 60% A, 40% B. Friday: 40% A, 60% B. Saturday and Sunday: 30% B, 70% C. A pinned day ignores tiers.
- (b) A and B every day, equal; C at weekends 50%.
- **Rec: (a)** (research §2.3). Fridays are a little harder; weekends are for fans.

**N6. The share grid.**
- (a) Rows always read in the same order, club to governorate, left to right in every language and app; a "?" tile shares as ⬜ (white), grey as ⬛, amber as 🟨, green as 🟩.
- (b) In `/ar`, rows read right to left like the page.
- **Rec: (a).** A grid that mirrors in some apps and not others is worse than one fixed order (research §4.1).

## Readings of the research the plan relies on

1. **The search list contains the answer.** Every active footballer is guessable, so the answer's name is in the page by design. The leak tests therefore check that the answer appears exactly as often as any other footballer in the page, the payload and the scripts, and never in an API response before the end (Task 12).
2. **The puzzle number is not stored.** `number = days since FIRST_DAY + 1`, computed. A stored number would break when the go-live date moves. `FIRST_DAY` is a constant set in Task 2 and moved to the go-live day in Task 16.
3. **`fast-check` is not installed.** Task 2 adds it (`pnpm add -D fast-check`), the sprint's only network use besides the pipeline's recorded fixtures.
4. **No `unstable_cache`.** Its doc says it "has been replaced by `use cache` in Next.js 16" (`03-api-reference/04-functions/unstable_cache.md`), and Cache Components are off in this repo (`next.config.ts`). Today's puzzle is memoised per server instance and, with Redis on, in Redis for 3 days. This also keeps a stale answer out of `.next/cache` between browser-test runs.
5. **One Upstash database for Production and Preview** (free plan: one database). Every key starts with `kora:{VERCEL_ENV or "local"}:`.
6. **Vercel Cron facts** (daily only on Hobby, run within the hour, production only, `Authorization: Bearer <CRON_SECRET>`) come from memory, not from a page read today. Task 10 step 1 checks vercel.com/docs/cron-jobs before coding. **[U]**

## Data model

Migration `prisma/migrations/<timestamp>_chkoun/migration.sql`, after Prisma's generated part:

```sql
ALTER TABLE puzzles ADD CONSTRAINT puzzles_source
  CHECK (source IN ('generator', 'pin', 'reserve'));
ALTER TABLE puzzles ADD CONSTRAINT puzzles_chkoun_has_player
  CHECK (game <> 'chkoun' OR player_id IS NOT NULL);
ALTER TABLE puzzles ADD CONSTRAINT puzzles_note_length
  CHECK (note IS NULL OR char_length(note) BETWEEN 1 AND 200);

-- A day freezes 48 hours before it starts (D-S2-2): no UPDATE or DELETE of a
-- row whose day is at most two days after today in Tunis. INSERT stays open
-- so an empty day can be filled once (the reserve).
CREATE FUNCTION puzzles_refuse_frozen() RETURNS trigger AS $$
BEGIN
  IF OLD.day <= (now() AT TIME ZONE 'Africa/Tunis')::date + 2 THEN
    RAISE EXCEPTION 'puzzle day is frozen: %', OLD.day USING ERRCODE = 'check_violation';
  END IF;
  RETURN CASE WHEN TG_OP = 'DELETE' THEN OLD ELSE NEW END;
END $$ LANGUAGE plpgsql;
CREATE TRIGGER puzzles_frozen BEFORE UPDATE OR DELETE ON puzzles
  FOR EACH ROW EXECUTE FUNCTION puzzles_refuse_frozen();

ALTER TABLE players ADD CONSTRAINT players_fame_tier
  CHECK (fame_tier IS NULL OR fame_tier IN ('A', 'B', 'C', 'D'));
ALTER TABLE players ADD CONSTRAINT players_fame_range
  CHECK (fame IS NULL OR (fame >= 0 AND fame <= 10));
ALTER TABLE players ADD CONSTRAINT players_photo_path_credited
  CHECK (photo_path IS NULL OR (photo_file IS NOT NULL AND photo_licence IS NOT NULL AND photo_source_url IS NOT NULL));
ALTER TABLE players ADD CONSTRAINT players_photo_path_shape
  CHECK (photo_path IS NULL OR photo_path ~ '^/photos/[a-z0-9-]+\.(jpg|png)$');

ALTER TABLE results ADD CONSTRAINT results_chkoun_score
  CHECK (game <> 'chkoun' OR score BETWEEN 1 AND 8);
```

TRUNCATE in `resetDatabase` does not fire row triggers, so test resets keep working. Test rows for frozen days are built relative to the Tunis date in SQL, never a fixed date.

`docs/schema.md` changes:
- `players` row: add "fame score, fame tier and the local star tag; the copied photo's path".
- `puzzles` row: "the day's answer for each game, with how it was chosen (generator, pin, reserve) and a note. Chkoun? puzzle numbers are computed from the day, not stored."
- `results` row: "a finished game, copied from Redis once a night (Chkoun?: guesses 1 to 8, the colour grid in `detail.grid`)".
- Rules table: `puzzles_chkoun_has_player`, `puzzles_source`, `puzzles_note_length`; "A day cannot change less than 48 hours before it starts" (`puzzles_frozen` trigger); `players_fame_tier`, `players_fame_range`, `players_photo_path_credited`, `players_photo_path_shape`; `results_chkoun_score`.
- A paragraph "Chkoun? calendar": generated 30 days ahead at deploy and nightly from a secret seed; the seed is not in the repo; a footballer who leaves the pool keeps his past puzzles.
- A paragraph "Results": kept in Redis for 8 days under `kora:{env}:chkoun:r:{day}`, copied to `results` nightly with `ON CONFLICT (game, day, visitor_id) DO NOTHING`.

Not stored: search keys and tile facts (built from the public `pool.json`), the seed, the token key, raw network addresses.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| **Redis is the only copy of a day's results for up to 24 hours, and the only copy of streaks.** An Upstash outage, an expired free database, or the keys never being set means results and streaks are not kept on the server; a copy that fails 8 nights in a row loses those days | Device storage always keeps the visitor's own streak; Redis errors fall back to "device" without breaking play; 8 days of life gives 7 retries; idempotent copy; `/admin/chkoun` shows the last job; Postgres holds every copied game, so streaks can be rebuilt from `results` later |
| Two streaks for one person (Facebook browser and Chrome have separate cookies and storage) | Said on the privacy page and in `stats.onDevice`/`onServer`; transfer code in Sprint 4 |
| The answer leaks (page, payload, scripts, photo path, card, logs) | Calendar only in the database; secret seed; `server-only` on facts and puzzle modules; card only at the end; leak tests on HTML, RSC payload, chunks and API responses; no ids in error messages |
| Replaying an older token lets a visitor undo a guess | Accepted: the recorded result is the first finished game (`HSETNX`); same as client-side daily games |
| Time zones and wrong phone clocks | One server function for the day; the client only displays `endsAt`; the server refuses another day's token; tests at 22:59:59 and 23:00 UTC; streak keyed on the puzzle number |
| The eligible list is too short after the fame filter | The window adapts (D-S2-5); band-level caps (D-S2-6); the "one field away" list in `/admin`; the local star tag; stop rule at 30 eligible |
| Neon wakes too often with Redis off | Puzzle memoised per instance; the free-tier table; a usage alert at 50% |
| A frozen answer becomes wrong (transfer) | It is kept (frozen is frozen); the admin flags it; tiles use the facts of `pool.json` at play time, so a transfer changes the club tile consistently for every visitor that day |
| Vercel Hobby cron limits differ from memory | Checked first in Task 10; the deploy top-up and the reserve keep the game running without the cron |
| Name search misses | CSV fixtures in CI; fame ranking; aliases; `chkoun_no_match` event without text |
| Strings arrive late | Drafts ship under P13 except country names; Task 12 lists the codes early |
| Photo licences | Only files with a stored licence and source page; no crop; credit on the card and on Sources; takedown contact |
